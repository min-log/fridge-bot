# 장보기·냉장고 관리 봇 설계

작성일: 2026-11-25
상태: 초안 (사용자 확인 전)

영수증 사진을 올리면 AI가 품목·가격을 뽑아 가구(냉장고) 재고에 넣고, 유통기한이 다가오면 알려 주고, 남은 재료와 저장한 레시피로 메뉴를 추천하고, "계란 남았어?" 같은 질문에 내 데이터를 조회해 답하는 PWA 서비스.

---

## 1. 결정 기록

## 2. MVP 기능 목록

### 2.1 인증·가구
- 구글·카카오 로그인, JWT 액세스 토큰(30분) + 리프레시 토큰(14일, Redis 저장, 로그아웃 시 삭제)
- 로그인 성공 시 프론트로는 60초짜리 1회용 코드만 넘기고, 프론트가 `POST /api/auth/token`으로 토큰과 교환함 (토큰이 URL·브라우저 기록에 남지 않게)
- 액세스 토큰은 응답 본문으로 주고 프론트는 메모리에만 보관. 리프레시 토큰은 HttpOnly·Secure·SameSite=Strict 쿠키(Path=/api/auth)
- 리프레시는 쓸 때마다 새로 발급(회전)하고, 이미 쓴 토큰은 다시 쓸 수 없음
- 액세스 토큰 검증은 Spring Security 리소스 서버(JwtDecoder)에 맡김
- 가구 만들기, 초대 코드로 참여, 초대 코드 재발급, 구성원 내보내기 (OWNER만)
- MVP에서는 사용자 한 명이 가구 하나에만 속함 (`household_members.user_id` 유니크). 여러 가구 소속은 2차

### 2.2 재고 관리
- 재고 등록(직접 입력 또는 영수증 확인 결과), 수정, 사용(수량 차감), 폐기
- 보관 위치: 냉장 / 냉동 / 실온
- 유통기한: 사용자가 입력하지 않으면 **카테고리별 기본 보관 일수 규칙**으로 계산 (AI 추정이 아니라 규칙이라 결과가 일정하고 테스트할 수 있음)
- 모든 변경은 `inventory_events`에 남김 (누가, 언제, 얼마나)
- 동시 수정: 낙관적 락(`@Version`). 충돌 시 409와 최신 상태를 돌려줌

### 2.3 영수증 인식
- 사진 업로드 → 202 응답 후 비동기로 AI 인식 → 프론트가 상태 조회
- AI가 가게 이름, 구매일, 품목(이름·수량·단위·단가·금액·카테고리), 합계를 추출 (Spring AI 구조화 출력)
- 사용자가 결과를 확인·수정한 뒤 "확정"하면 재고와 지출 내역에 반영
- 같은 이미지를 다시 올리면 중복으로 막음

### 2.4 유통기한 알림
- 매일 09:00(Asia/Seoul) 스케줄러가 D-3, D-1, D-day 품목을 찾아 가구 구성원에게 Web Push
- 같은 품목·같은 단계 알림은 한 번만 보냄

### 2.5 대화형 질의 (Tool calling)
- "계란 남았어?", "이번 주 식비 얼마 썼어?", "내일 버려야 할 거 있어?" 같은 질문에 LLM이 내 API를 도구로 호출해 답변
- MVP의 도구는 **조회만** 제공. 재고 차감 같은 쓰기는 LLM이 "제안"을 돌려주고 사용자가 화면 버튼으로 확정함

### 2.6 메뉴 추천 (RAG)
- 레시피 등록(직접 입력, 공공 레시피 시드 데이터) → 임베딩 저장
- 유통기한이 가까운 재료를 우선해 레시피를 검색하고, LLM이 검색된 레시피 안에서만 골라 이유와 함께 3개 추천

### 2.7 식비 통계
- 확정된 영수증 기준 월별 합계, 카테고리별 합계, 전월 대비

### 2차로 미룸
- 장보기 목록 자동 생성(부족한 재료 → 장보기 목록), 바코드 인식, 여러 가구 소속, 대화 응답 스트리밍(SSE), MCP 서버, 이미지 S3 저장, 쓰기 도구(LLM이 바로 재고 차감)

## 3. 시스템 구성

```
[PWA (React)] ──HTTPS──> [Caddy: 정적 파일 + /api 프록시]
                                   │
                                   v
                           [Spring Boot 앱] ──> Claude API (영수증·대화·추천)
                             │      │      └──> OpenAI API (임베딩)
                             v      v
                  [PostgreSQL+pgvector] [Redis]
```

- Lightsail 2GB 한 대에 Docker Compose로 `caddy`, `app`, `postgres`(pgvector/pgvector:pg17), `redis`(redis:8-alpine) 실행
- 메모리 상한(초안): app 768MB, postgres 384MB, redis 64MB, caddy 64MB
- 영수증 이미지는 서버 볼륨(`/data/uploads`)에 저장, 90일 뒤 삭제 (S3는 2차)
- 휴대폰 사용: 배포 후에는 HTTPS 도메인으로 어디서나 접속하고, 홈 화면에 PWA로 설치해 앱처럼 씀 (카메라 업로드·Web Push는 HTTPS가 필요함). 배포 전(1~5주차)에 밖에서 시험하려면 로컬 서버를 Cloudflare Tunnel로 임시 HTTPS 주소에 연결함
- 백엔드 패키지는 기능 단위로 나눔: `auth`, `household`, `inventory`, `receipt`, `recipe`, `chat`, `stats`, `notification`, `ai`(공통: 사용량 기록·제한·폴백)

## 4. DB 테이블

공통: PK는 `bigint` identity, 시간은 `timestamptz`, 생성·수정 시각 컬럼(`created_at`, `updated_at`)은 생략하고 적음.

| 테이블 | 주요 컬럼 | 설명 |
|---|---|---|
| `users` | id, email, nickname, provider(GOOGLE/KAKAO), provider_id | 유니크 (provider, provider_id) |
| `households` | id, name, invite_code, invite_code_expires_at | 초대 코드 유니크 |
| `household_members` | household_id, user_id, role(OWNER/MEMBER), joined_at | PK (household_id, user_id), MVP는 user_id 유니크 |
| `inventory_items` | id, household_id, name, category, quantity numeric(10,2), unit, location(FRIDGE/FREEZER/PANTRY), expires_on date, purchased_on, receipt_item_id null, status(ACTIVE/CONSUMED/DISCARDED), version | 인덱스 (household_id, status, expires_on) |
| `inventory_events` | id, item_id, user_id, type(ADD/CONSUME/DISCARD/ADJUST), quantity_delta, created_at | 변경 이력, 소비 통계에 사용 |
| `category_shelf_life` | category, location, default_days | 유통기한 기본값 규칙 (Flyway 시드) |
| `receipts` | id, household_id, uploaded_by, image_path, image_sha256, store_name, purchased_on, total_amount, status(UPLOADED/PARSING/PARSED/FAILED/CONFIRMED), failure_reason, version | 유니크 (household_id, image_sha256) |
| `receipt_items` | id, receipt_id, raw_name, name, category, quantity, unit, unit_price, amount, excluded bool | 사용자가 수정한 최종값 저장. excluded=재고에 넣지 않을 품목(봉투 등) |
| `recipes` | id, household_id null, title, ingredients(text), steps(text), source, created_by, embedding_status(PENDING/DONE/FAILED) | household_id null = 공용 시드 레시피 |
| `vector_store` | id uuid, content, metadata jsonb, embedding vector(1536) | Spring AI PgVectorStore 표준 테이블. metadata에 recipe_id, household_id. HNSW 인덱스 |
| `spring_ai_chat_memory` | conversation_id, content, type, timestamp | Spring AI JDBC ChatMemory 표준 테이블 |
| `push_subscriptions` | id, user_id, endpoint, p256dh, auth | endpoint 유니크 |
| `notification_logs` | id, item_id, user_id, stage(D3/D1/D0), sent_at, success | 유니크 (item_id, user_id, stage)로 중복 발송 방지 |
| `ai_usage_logs` | id, household_id, user_id, feature(RECEIPT/CHAT/RECOMMEND/EMBED), model, input_tokens, output_tokens, cost_usd numeric(10,6), latency_ms, success, error_code, created_at | 월 비용·실패율 집계 |

Redis 키 (모든 키에 TTL을 두고 `volatile-lru` 정책 사용):

| 키 | 용도 | TTL |
|---|---|---|
| `login:code:{code}` | 소셜 로그인 후 1회용 코드 → userId (GETDEL로 한 번만 사용) | 60초 |
| `rt:{userId}:{sha256(token)}` | 리프레시 토큰 (원문은 저장하지 않음, DEL 성공 여부로 회전) | 14일 |
| `receipt:lock:{householdId}:{sha256}` | 같은 영수증 동시 업로드 방지 (SETNX) | 10분 |
| `rec:{householdId}:{재고해시}` | 메뉴 추천 결과 캐시 | 6시간 |
| `ai:quota:{userId}:{yyyyMMdd}:{feature}` | 사용자별 하루 AI 호출 횟수 (INCR) | 1일 |
| `ai:cost:{yyyyMM}` | 이번 달 누적 비용 (빠른 상한 확인용, 원본은 DB) | 40일 |

## 5. API 목록

공통: `/api` 아래, 인증은 `Authorization: Bearer`, 오류는 RFC 9457 `ProblemDetail` 형식. 가구 범위 데이터는 모두 서버가 JWT의 사용자로 가구를 찾아 조회하며, 요청에 household_id를 받지 않음.

|---|---|---|
| 인증 | GET `/oauth2/authorization/{google\|kakao}` | 소셜 로그인 시작 |

| | GET `/api/me` | 내 정보·소속 가구 |
| 가구 | POST `/api/households` | 가구 만들기 |
| | GET `/api/households/me` | 내 가구·구성원 |
| | POST `/api/households/invite-code` | 초대 코드 재발급 (OWNER) |

| | POST / DELETE `/api/push/subscriptions` | 구독 등록·해제 |
| 운영 | GET `/api/ai-usage?month=2026-12` | 우리 가구 AI 사용량·비용 |
| | GET `/actuator/health` | 배포 후 헬스 체크 |

## 6. AI 활용 지점과 실패 처리

### 6.1 공통 (ai 패키지)
- 모든 AI 호출은 `AiGateway` 한 곳을 거침: 호출량 제한 확인 → 월 비용 상한 확인 → 호출(타임아웃·재시도) → 토큰·비용·지연 기록(`ai_usage_logs`) → 실패 시 기능별 폴백
- 재시도: 타임아웃, 429, 5xx만 최대 2회, 지수 백오프(1s, 3s). 400·인증 오류는 재시도하지 않음
- 하루 호출 제한(초안): 영수증 20회, 대화 50회, 추천 20회 / 사용자. 초과 시 429와 안내 문구
- 월 비용 상한(초안): 5달러. 넘으면 AI 기능은 폴백만 동작하고 로그에 경고
- 모델 이름·키·상한은 모두 환경변수(`AI_CHAT_MODEL`, `AI_RECEIPT_MODEL`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `AI_MONTHLY_BUDGET_USD` 등)
- 영수증 인식은 처음에 상위 모델로 시작하고, 영수증 20장 정도로 하위 모델과 정확도·비용을 비교해 결과를 기록함

### 6.2 지점별 정리

| 지점 | 방식 | 검증 | 실패 시 처리 |
|---|---|---|---|
| 영수증 인식 | 이미지(Media) + 프롬프트 → 구조화 출력(`ReceiptParseResult` 레코드) | 수량·금액 > 0, 품목 금액 합 ≈ 합계(차이 5% 이내가 아니면 경고 표시), 모르는 카테고리는 "기타", 이미지 10MB 이하·jpg/png/heic | 재시도 후에도 실패하면 `FAILED` + 사유 저장. 화면에서 "다시 시도" 또는 "직접 입력"으로 이어감. JSON 파싱 실패도 같은 처리 |
| 대화형 질의 | ChatClient + `@Tool` 메서드: `searchInventory(name)`, `listExpiringItems(days)`, `getSpendingSummary(from, to, category)`, `suggestConsume(itemName, quantity)`(제안만 반환) | 도구는 **가구 ID를 LLM 인자로 받지 않고** 서버가 `ToolContext`로 넣음 → 다른 가구 데이터 조회 불가. 한 요청당 도구 호출 5회 제한, 날짜 범위 최대 1년 | "지금은 답변할 수 없어요" + 재고·통계 화면 링크. 도구 실행 중 예외는 LLM에 오류 메시지로 돌려주고 답변을 계속하게 함 |
| 메뉴 추천 (RAG) | 임박 재료 + 보유 재료로 질의문 생성 → pgvector 유사도 검색(topK 8, 필터: 내 가구 또는 공용) → LLM이 검색된 레시피 안에서만 3개 선택, 레시피 ID와 이유를 구조화 출력 | 응답의 레시피 ID가 검색 결과에 있는지 확인 (없는 레시피를 만들어 내면 제외) | LLM 실패 → 벡터 검색 상위 3개를 이유 없이 반환. 임베딩 실패 → 재료 이름 일치 개수로 정렬하는 SQL 검색. 결과는 Redis에 6시간 캐시, 재고가 바뀌면 키가 달라져 자연히 새로 계산 |
| 레시피 임베딩 | 레시피 하나 = 문서 하나 (짧아서 분할하지 않음). 제목 + 재료 + 요약을 임베딩 | — | 실패 시 `embedding_status=PENDING`으로 저장, 10분마다 스케줄러가 다시 시도. 3번 실패하면 `FAILED` |

### 6.3 레시피 시드 데이터
- 후보: 식품의약품안전처 "조리식품의 레시피 DB" 공공 API. 이용 조건(출처 표시 등) 확인 후 100~200개를 Flyway가 아닌 별도 적재 명령으로 넣음

## 7. 테스트·CI·비밀값

### 테스트
| 단계 | 대상 | 도구 |
|---|---|---|
| 단위 | 재고 차감·상태 전이, 유통기한 기본값 계산, 영수증 결과 검증, 비용 계산, 알림 대상 선정 | JUnit 5, AssertJ, Mockito |
| 웹 슬라이스 | 컨트롤러 요청 검증·권한·오류 형식 | `@WebMvcTest`, Spring Security Test |
| 통합 | 저장소·Flyway·pgvector 검색·Redis 캐시·영수증 확정 트랜잭션·동시 차감(낙관적 락) | `@SpringBootTest` + Testcontainers(`pgvector/pgvector:pg17`, `redis:8-alpine`) + `@ServiceConnection` |
| AI | ChatModel·EmbeddingModel을 고정 응답 스텁으로 바꿔 흐름·폴백·재시도 검증 | 스텁 빈 |
| 실제 AI | 실제 API로 영수증 샘플 인식 정확도 확인 | `@Tag("llm")`, CI에서 제외하고 수동 실행 |

- 커버리지: JaCoCo 리포트, 서비스·도메인 계층 70% 이상을 목표로 함 (CI 실패 조건은 6주차 이후 적용)

### CI/CD (GitHub Actions)
- PR·push: `backend/` 변경 시 `./gradlew check`(테스트 + JaCoCo), `frontend/` 변경 시 lint·build, 모든 PR에 gitleaks 비밀값 검사
- main 머지: 백엔드 이미지 빌드 → GHCR 푸시 → SSH로 서버에서 `docker compose pull && up -d` → `/actuator/health` 확인, 실패 시 이전 이미지 태그로 되돌림
- Dependabot으로 Gradle·npm·Actions 의존성 업데이트

### 비밀값
- `application.yml`은 `${ANTHROPIC_API_KEY}`처럼 기본값 없이 참조만 함. 값이 없으면 앱이 뜨지 않게 함
- 로컬: `.env`(커밋 안 함) + `.env.example`(빈 값, 커밋)
- 서버: `.env` 파일을 서버에만 두고 권한 600. GitHub에는 배포용 SSH 키·호스트만 Secrets로 저장
- 첫 커밋 전에 `.gitignore`에 `.env*`(단 `!.env.example`), `*.pem`, `*.key` 추가
- git remote는 SSH 주소 사용, 토큰을 URL에 넣지 않음
