# 0004. 리프레시 토큰은 Redis에 해시로 저장하고 쓸 때마다 회전한다

- 상태: 채택
- 날짜: 2026-11-25

## 배경
액세스 토큰(JWT)은 짧게(30분) 두고 리프레시 토큰으로 갱신한다. 리프레시 토큰은 오래 살기 때문에 로그아웃·강제 만료가 가능해야 하고, 탈취되면 피해를 줄여야 한다.

## 결정
- 리프레시 토큰은 JWT가 아닌 불투명한 임의 문자열 `{userId}.{32바이트 임의값}`이다.
- Redis 키는 `rt:{userId}:{sha256(임의값)}`, TTL 14일. 원문은 저장하지 않는다.
- 갱신할 때 키를 `DEL`하고 지워졌을 때만 새 토큰을 발급한다(회전). 이미 쓴 토큰은 다시 쓸 수 없고, 같은 토큰으로 동시에 두 번 요청해도 한쪽만 성공한다.
- 로그아웃은 키를 지우고 쿠키를 만료시킨다.
- 전달: 리프레시 토큰은 `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` 쿠키, 액세스 토큰은 응답 본문으로 주고 프론트는 메모리에만 둔다.

## 검토한 대안
- 리프레시 토큰도 JWT로 발급: 서버에 상태가 없어 간단하지만 개별 폐기가 어렵다.
- DB 테이블에 저장: 가능하지만 TTL 만료를 직접 지워야 하고, 이 용도에는 Redis TTL이 더 맞다.
- 재사용이 감지되면 그 사용자의 모든 토큰 폐기: 보안상 강하지만, 사용자 ID만 알면 임의 문자열로 다른 사람을 로그아웃시킬 수 있어 MVP에서는 넣지 않았다.

## 결과
- Redis 데이터가 새어도 원문 토큰을 알 수 없다.
- 액세스 토큰은 새로고침하면 사라지므로 프론트가 앱 시작 시 `/api/auth/refresh`를 한 번 호출해야 한다.
- 테스트: 회전 후 이전 토큰 401, 로그아웃 후 401, 위조 토큰 401 (`AuthFlowIntegrationTest`).
